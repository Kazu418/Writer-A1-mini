# 所有者側の受取・実機操作

この文書は所有者が自分の A1 mini を操作するときに読む。友人側の作業は [FRIEND_WORKFLOW.md](FRIEND_WORKFLOW.md) のZIP提出まで。固定の寸法・座標・Z・速度の正本は [MACHINE_CONSTRAINTS.md](MACHINE_CONSTRAINTS.md)。

## 1. 受け取ったものを確認する

1. 信頼するローカル環境へZIPを展開する。
2. 同梱の `manifest.json`、`approval.json`、プレビューを確認する。承認されたPDFとジョブが同じ版か照合する。
3. `scripts/prepare_handoff.py verify <展開先>` で再検証する。提出後の修正、旧版の混入、別機種のプロファイルを検知したら実行しない。
4. 面数・タイル順・紙番号を確認する。`face1-pass2` 等のファイル名の数字を、紙の枚数と混同しない。
5. 既存のノートを印刷済みなら、これから書くタイルを明示する。以前印刷したタイルを「最初から」の指示で重ね書きしない。

友人が承認した見た目が目的。所有者側で再スライス・自動フィット・再組版をしてから印刷すると、承認されたファイルとは別物になる。

## 2. ホームと取り付け

1. 実行中ジョブがないこと、ヒーターの状態、エラー/HMSを確認する。
2. **ペンをホルダーから外したことを、人が確認する。** 「いけるはず」は、装着状態を観測した証拠ではない。
3. ペンなしでホームする。通信で送れたことだけでなく、実機の全軸ホーム状態も確認する。
4. ノズルを退避高さへ上げてから、対象タイルの **最初の筆記XY** へ移動する。始点はジョブ内の最初の `G1 X... Y...`/manifestから取る。タイル1の座標を全タイルへ使い回さない。
5. ペンなしのまま、取り付け基準のZへ低速下降する。
6. 停止を見てから、ペン先が紙に軽く触れる位置で固定する。スプリングを強く押し込まない。
7. 人が取り付け完了を伝える。
8. **XYを動かす前にペンを浮かせる。** 転送・本体の開始処理より先に、垂直退避を行う。

今回の実例でタイル1とタイル2の始点は、それぞれおおむねX14/Y172、X12.5/Y159.5だった。これは今回の文章の最初の線の位置であり、装置の固定原点でも、すべてのノートの始点でもない。

## 3. 紙の置き方

- A4の左右をプレート中央へ合わせる。紙を平らにし、ペンやノズルの走行範囲へ厚いクリップを置かない。
- 各面のpass1は紙上端を奥端へ、pass2は紙下端を手前端へ合わせる。
- タイル2へ進むとき、紙を「1タイル分くらい」動かすのではなく、下端を手前端へ合わせる。
- 裏面は上端を上のままページをめくる向きに返し、同じpass1/pass2の置き方を使う。
- 紙を動かした後は、固定、表裏、紙番号、passを再確認する。上下のわずかな誤差は継ぎ目の行間に出る。

紙の交換や固定をしている最中に、接触したペンがXY移動しないようにする。

## 4. 開始・監視

1. 納品の有効プロファイルを使い、対象ジョブを独立検査する。
2. 最新状態で全軸ホーム済み、停止中、エラー/HMSなし、ヒーター目標OFFを確認する。
3. 転送方式が独自マクロを加えないことを確認する。今回の運用はMQTT/FTPSによる直接送信を使った。
4. 転送後に読み戻し、送信元とバイト単位で同じことを確認する。
5. 開始命令は一度だけ送る。開始済みの記録を残し、タイムアウトやACK欠落を理由に再送しない。
6. 状態の `RUNNING` を確認する。これは実行中という報告であり、筆跡の位置や濃さが正常という証明ではない。
7. 最初の文字のXYと接触を人が見る。細かい文字、ペンの揺れ、紙の引っかかりも観察する。

通信接続は機器の証明書を照合し、認証情報をログへ出さない。機器IDや接続先を、共有の生成用プロファイルへ混ぜない。旧試行スクリプトはそのまま実行せず、所有者の現在の設定・機種・ジャーナルと照合する。

## 5. 中断と再開

「止めて」は最優先。まず動作を止め、停止状態を確認してから原因を調べる。

- 通常のキャンセルはホーム状態を失うことがある。停止前にホーム済みだったという理由で再開しない。
- 一時停止でも、今回の実機はノズル目標温度を変更した。監視処理がそれを異常と判定してキャンセルした実例がある。ホーム保持を前提に紙交換を約束しない。
- 高さが合わない場合は、ペンを外してホーム状態を復旧し、取り付け基準から合わせ直す。低いペンを装着したまま再ホームしない。
- 既に書いた紙へ最初から再実行すると重ね書きになる。別紙に変えるか、そのタイルを最初から書き直すかを人が決める。
- 実機状態が曖昧、送信結果が不明、紙の固定が変わった場合は、推測でG-codeの原点を変更しない。

再開は新しい試行ID/ジャーナルを使う。以前の `start_sent` 記録を削除して重複開始防止を迂回しない。

## 6. 完了

`FINISH`、エラーなし、ペン上げ/停止を確認してから紙やペンを扱う。紙や装着状態の物理確認と通信の状態を両方記録する。単に「命令がACKされた」「検証器がvalidを返した」は、ノートの完成とは別の確認。

所有者が実際に確認したタイル、字の読みやすさ、紙/ペン/ホルダーの変更、問題を記録し、次の依頼へ引き継ぐ。今回の会話ではタイル1の完成を本人が確認し、その後タイル2を開始した。タイル2以降の完成まで自動的に確認済みにしない。

## 共有コピーの実機操作ガード

共有用コピー内の歴史的なMQTT/FTPS・位置合わせスクリプトは、通常の状態ではモジュール読み込み時に停止する。これは友人の生成工程から実機操作を分けるためのガードで、実機準備が済んだという証明ではない。

所有者が自分の環境で履歴スクリプトを検討する場合だけ `WRITER_A1_MINI_OWNER_CONTROL=1` を明示する。その上で接続先・機種・証明書・認証情報の取得先・対象タイル・重複送信防止ジャーナルを確認する。認証情報は所有者のローカル環境に置き、Gitや納品ZIPへ入れない。友人側ではこの環境変数を有効化せず、`scripts/prepare_handoff.py`だけを使う。

旧スクリプトのホスト名やファイル名をそのまま現在の依頼へ適用しない。新しい納品形式の`face-001-pass-1`と、履歴の`face1-pass1`は別の命名であり、所有者のAgentがmanifestの対応を確認する。実機接続に使う追加依存`paho-mqtt`は所有者側だけのもので、オフライン生成には不要。
