# 友人のノートを所有者の A1 mini 用に準備する

## 目指すやり取り

友人はノートと希望を Agent に渡す。Agent が実機の制約に合うノートを組み、実際の筆記軌跡の PDF を見せる。友人が承認した版について、同じデータの PDF・G-code・実行順・チェックサムをまとめて所有者へ渡す。所有者が紙とペンを準備し、自分の装置で実行する。

この工程はオフライン。友人側にプリンターの認証情報や所有者の Mac の設定は必要ない。

## 1. 最初に確認すること

Agent は原本を読んでから、以下の未指定項目をまとめて確認する。既に答えがある項目は聞き直さない。

| 項目 | 確認内容 |
|---|---|
| 原本 | PDF、画像、Goodnotes 書き出し、テキストなど。どれが正本か |
| 枚数 | A4 **何枚**に抑えるか。片面か両面か。例: A4 1枚両面 = 2面 = 4タイル |
| 文字 | 希望サイズ、読みやすさと収容量の優先順位。以前の実例は本文2.8mm |
| 内容 | 全文を残すか、要約・省略が許されるか。必須の項目は何か |
| 公式 | すべて書くか、**別枠の数学の公式だけ**手書き用に空白にするか |
| 書体 | 標準のストローク字体か、用意された本人字庫か。欠字の代替を許すか |
| 納品先 | 所有者へ渡す方法。ZIP/共有フォルダ/承認済みコミットなど |

書体は本文全体だけでなく、強調キーワードだけ変える指定も扱う。今回の追加実例は、裏面の下線付きキーワードだけを本人字庫から標準手書き風ストロークへ変更し、下線とその他の筆記座標を保つもの。`plotnote.keyword_style.fit_standard_keyword`は元のキーワードのインク矩形に比率を保って収める。段落全体の縮小・詰め直しとは区別し、変更後の実G-codeプレビューを本人に確認する。

「何ページ」は曖昧なので、例えば「A4 1枚の両面、計2面・4ジョブ」で確認する。書体サイズは PDF の pt と mm を混同しない。1mm = 72/25.4 pt。

画像やスキャンは、そのまま図形としてトレースしない。内容の読取/OCR、文字・数式の校正、線画化を行ってから、描画用のテキスト/ベクターへ組み直す。既存の汎用 PDF 入力器が画像を拒否した場合に、黙って画像部分を捨てない。

**完了条件:** 原本、物理枚数、面数、文字サイズ方針、内容方針、公式の扱いが記録されている。

## 2. 内容を構造化する

見出し、段落、箇条書き、図、表、数式を分け、原本との対応を残す。数値・符号・添字は校正する。図のタイトルや本文を残しても、肝心の図だけ落ちていたら完了ではない。

「公式だけ空白」の分類は、次の実例に従う。

- 空白にする候補: 分散・標準偏差・共分散・相関係数など、分数・Σ・√・添字で別枠に組んだ数学の公式。
- 残すもの: 文章中の `IQR=Q3−Q1`、階級数の文字式、外れ値の上限/下限、変数の意味、`n=全体の人数` などの説明、文字で記した関係、図表内の数値。
- 数式が文中か別枠かだけで意図が決まらない原稿は、具体例を本人に見せて分類を確認する。

式の除去は意味を付けたブロック単位で行う。`=`、英字、数字、記号の有無だけで全原稿を消去しない。空白の縦横寸法を保持し、残したテキストを詰めない。新しく組版する場合も、本人が書き足すスペースの広さをプレビューで確認する。

**完了条件:** 内容一覧と削除/空白対象の一覧があり、残す文字式・説明が残っている。

## 3. 固定の描画窓へ配置する

[MACHINE_CONSTRAINTS.md](MACHINE_CONSTRAINTS.md) の描画窓と紙の置き方を使う。Agent がこの装置を再設計・再校正する必要はない。

A4 の各面を、上側/下側の **165×127.5mm の2枚のタイルSVG** として作る。タイルのローカル座標は左上原点、X右/Y下、mm。出力ファイル名だけで読み順を推測させず、紙番号・表裏・pass番号をリクエストに記す。

- 文字と図の線は中心線。文字の輪郭を二重になぞる方式へ変えない。
- 全ストロークを窓の内側へ入れる。曲線や線幅の端も含めて検査する。
- 境界で文字や公式を分断しない。図が収まらない場合は、次の面への移動やサイズ変更を明示する。
- 十字の位置合わせ印、タイルを囲う枠、試し書きは追加しない。原稿の表・図の枠は残す。
- 収まらないときは本人に選択を返す。「全文のまま紙を増やす」「文字を小さくする」「指定部分を省く」を具体的に示す。

例: 以前のノートを2.8mmから1.5倍の4.2mmへ拡大した計算では、必要な段組み高さは約1641.7mm、A4両面の利用枠は計988mm。元の枚数には収まらなかった。文字の寸法変更は面積にも効くため、単純に現在位置のまま拡大して完成とはしない。

**完了条件:** 希望枚数内に全項目が収まるか、収まらない量と代案を本人が判断できる。

## 4. オフラインの納品用ファイルを生成する

環境の用意はリポジトリのルートで行う。動く最小例は `examples/handoff/request.json` と同じディレクトリの2枚のSVG。

```sh
sh scripts/bootstrap.sh
```

以下が固定装置用の入口。`plotnote export` の汎用プロファイルを独自に書き換えて代用しない。

```sh
.venv/bin/python scripts/prepare_handoff.py prepare \
  --request requests/my-job.json \
  --output jobs/my-job
```

リクエスト例:

```json
{
  "job_id": "my-job",
  "max_sheets": 1,
  "duplex": true,
  "font_size_mm": 2.8,
  "formula_policy": "blank_display_formulas",
  "faces": [
    {
      "sheet": 1,
      "side": "front",
      "pass1": "tiles/front-pass1.svg",
      "pass2": "tiles/front-pass2.svg"
    },
    {
      "sheet": 1,
      "side": "back",
      "pass1": "tiles/back-pass1.svg",
      "pass2": "tiles/back-pass2.svg"
    }
  ]
}
```

SVG の相対パスはリクエストJSONのある場所から解決する。上記なら `requests/tiles/` 内。`formula_policy` は `keep` または `blank_display_formulas`。これは意味の記録であり、既に線になった SVG から公式を自動推論して消す機能ではない。Agent が前工程で正しく内容を用意する。

`font_size_mm` も希望サイズの記録。文字がすべてパスへ変換済みなら、検証器はそのパスから漢字のemサイズや意味を復元できない。正しいサイズ・内容・可読性は本人のプレビュー確認で担保する。

生成後に再検証する。

```sh
.venv/bin/python scripts/prepare_handoff.py verify jobs/my-job
```

固定機械プロファイルは `profiles/a1-mini-owner-v1.json`。ノートによるレイアウトの違いと、装置のプロファイルの違いを分ける。第三者のA1用スタートコードやBambu Studioの再スライスを途中へ挟まない。

**完了条件:** 全タイルの生成・再読込・機械範囲・プロファイル・チェックサムの検査が通る。エラーを警告に落として提出しない。

## 5. 本人がプレビューを承認する

`jobs/my-job/preview.pdf` を本人に開いて見せる。これは実際の生成G-codeの量子化された座標をA4へ戻したもの。入力の文字フォントのスクリーンショットではない。

本人が確認するもの:

- 内容が揃っている。数値・符号・添字が正しく読める。
- 本文の大きさと字間・行間が許容できる。
- 図の文字が枠や線へ重ならない。
- 空白にした公式と、残す文字式・説明が意図どおり。
- 指定した紙の枚数・表裏・タイルの継ぎ目が合っている。

本人に「このノートでよいか」を確認し、承認されたPDFのSHA-256を用いて記録する。

```sh
.venv/bin/python scripts/prepare_handoff.py approve jobs/my-job \
  --reviewer 'ノート本人の名前' \
  --preview-sha256 <本人が確認したPDFのSHA-256>
```

Agent が本人の承認を先回りして記録しない。PDF、G-code、プロファイル、入力が変われば承認し直す。承認時点の内容と納品時点の内容をハッシュで対応付ける。

## 6. 所有者へ渡す

```sh
.venv/bin/python scripts/prepare_handoff.py bundle jobs/my-job \
  --output deliveries/my-job.zip
```

納品には、最低限以下を含める。

| ファイル | 用途 |
|---|---|
| `preview.pdf` | 本人が承認したA4実寸の両面/各面プレビュー |
| `request.json` | 枚数・表裏・文字サイズ・公式方針など |
| `inputs/*.svg` | 各タイルの再生成元 |
| `machine-contract.json` | 納品物に固定された所有者用の機械契約 |
| `gcode/*.gcode` | 実際の筆記データ |
| `gcode/*.gcode.3mf` | 同一G-codeを格納するBambuコンテナ |
| `gcode/*profile*.json` | 各passの有効な校正設定 |
| `manifest.json` | ファイルのハッシュ、紙/面/passの順序、最初の位置など |
| `approval.json` | 本人が確認した版の承認記録 |

所有者には「A4何枚、片面/両面、何ジョブ、どの順序、どのプレビューを承認したか」を添えてZIPを渡す。友人側Agentは、本番開始まで進めず、渡すところで止まる。認証情報や機器の実識別情報は含めない。

この工程の完了は、**本人が承認したバイト列の検証済みZIPを所有者が受け取れる状態**。ファイルを生成しただけ、プレビューを作っただけ、旧版のリンクを渡しただけでは完了ではない。
